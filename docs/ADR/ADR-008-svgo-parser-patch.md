# SVGO parser patch delivery

Transform uses SVGO 4.1.0 with the Node parser changes from [svg/svgo#2224](https://github.com/svg/svgo/pull/2224). They make SAX's entity expansion limit configurable. Transform accepts an optional `svgMaxEntityCount` setting and forwards it only when explicitly configured. With no setting, Transform passes no entity limit to SVGO, preserving SVGO's own default. Draw.io metadata can exceed that default; see [svg/svgo#2218](https://github.com/svg/svgo/issues/2218).

If SVG inlining reaches the entity limit, Transform keeps an ordinary image reference and emits a warning; CLI Markdown builds likewise keep the original image markup. Only the counted-entity parser error triggers this fallback. Malformed XML and other failures remain errors. Warnings and direct helper errors identify `content.svgMaxEntityCount` and `--svg-max-entity-count`.

For a document that needs to preserve inlining with a higher limit, configure `transform(markdown, {svgMaxEntityCount: 1024})`. In CLI, set `content.svgMaxEntityCount: 1024` in `.yfm` or pass `--svg-max-entity-count 1024`; the CLI flag overrides the config. Choose a limit for the document rather than raising it globally.

The version-specific patch lives in `patches/svgo+4.1.0.patch`. It changes the ESM parser and optimizer, native SVGO CLI, generated CommonJS entry used by Transform, and generated TypeScript declarations. The browser bundle is unused by this integration and remains unchanged.

`prepare` attempts the patch without blocking installation when development dependencies are absent or incompatible, and always attempts Husky setup. This supports `npm ci --omit=dev`. `build:lib` and `prepack` require the patch to succeed and reject a missing or incompatible SVGO version. `prepack` reapplies the patch idempotently. The helper resolves the actual installation directory for standalone and hoisted npm workspaces. After installing with scripts disabled, run `npm run patch:svgo` before tests or builds.

SVGO is a development dependency. `build:lib` applies the patch, compiles TypeScript, then bundles the patched adapter and its runtime dependencies into `lib/svgo.js`. Generated third-party notices are included in `lib/svgo.LICENSES.txt`. The published package neither fetches SVGO nor runs a patching install script: all of the Node parser code is already present in its internal module. The published `src` tree is reference source, not an independently buildable distribution: its adapter imports the development dependency. Build from a development checkout with dev dependencies installed; consumers execute the compiled `lib` entry points.

The isolated module avoids placing SVGO's dependency tree in the consumer's `node_modules`. Shipping that tree with npm `bundleDependencies` was rejected after an existing CLI installation placed `htmlparser2` beside a bundled, incompatible `entities` version. Keeping dependency code inside the module isolates both npm and pnpm consumers from this collision.

`npm run test:package` builds Transform, packs it, extracts the tarball, and exercises the isolated module through CommonJS and ESM without any installed dependencies. It checks the explicit limit, unchanged parser default, multipass, per-call isolation, and third-party notices. It also installs the tarball into a clean consumer with no SVGO dependency and compiles the public Transform, Markdown and images declarations using `skipLibCheck: false`. The private adapter declaration may reference SVGO, but public declarations must not reach it. The package check runs in the shared Quality workflow after the build. `test/svgo-entities.test.ts` exercises the Transform configuration, default image fallback, explicit upper bound, unrelated parser errors, and per-call isolation. Lifecycle tests cover missing dev dependencies, incompatible versions, patch failures, and Husky setup. Regressions must use counted numeric references: predefined XML entities such as `&amp;` alone do not trigger SAX's counter.

After upstream releases the option, upgrade the exact development dependency and remove the patch and its prepare/prepack helpers. Keep the counted-entity integration and package regressions. Recheck the adapter's type-only import against upstream declarations and update DEP-0001. The isolated module can remain the delivery boundary when the local patch is removed.
