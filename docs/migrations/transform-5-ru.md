# Миграция с Transform 4 на Transform 5

**Язык:** [English](transform-5.md) | Русский

Это руководство предназначено для приложений и авторов пакетов, которые используют
`@diplodoc/transform` напрямую или получают его через редактор, CLI либо расширения.
Оно описывает контракт подготовленного исходного кода Transform 5 и помогает
оценить и выполнить переход на доступный, проверенный артефакт.

Для проверки мажора используйте `5.0.0-beta.1` из канала `transform5`.
Сначала подтвердите доступность точной версии, затем установите её:

```sh
npm view @diplodoc/transform@5.0.0-beta.1 version
npm install @diplodoc/transform@5.0.0-beta.1
```

У расширений этого графа тоже beta-версии с новыми мажорами. Если приложение
объявляет их напрямую, используйте Utils `3.0.0-beta.2`, Directive `1.0.0-beta.2`,
Cut `2.0.0-beta.1`, Tabs `4.0.0-beta.1`, File `1.0.0-beta.1` и Notes `1.0.0-beta.1`.
Обычный диапазон стабильного мажора
не включает его beta. Не используйте `--force` для обхода peer dependencies.
Для библиотеки отдельно согласуйте peer range на конкретную beta.

Стабильный Transform 5 ещё не выпущен, `latest` остаётся в линии 4. Локально
проверенные исправления совместимости старых хостов могут быть не опубликованы;
ограничения смешанного графа 4 и 5 описаны ниже. Наличие исходников или успешная
локальная проверка не доказывает доступность версии в реестре и внедрение у потребителей.

## Коротко

1. Найдите реальные вызовы Transform, плагины, Markdown и браузерные ресурсы;
   проверьте установленный граф и peer dependencies каждого хоста.
2. Подготовьте Node.js **24+**; при использовании npm нужен **11.5.1+**.
   Проверьте свои плагины на markdown-it **15**. При необходимости сохраните отдельную настоящую копию 4.
3. Для прежнего результата явно включите нужные общие атрибуты и передайте
   highlighter. Проверьте таблицы, изображения, SVG и собственные callback-списки.
4. При повторном использовании парсера храните контекст каждого документа и
   передавайте его при компиляции. Проверьте обработку вложенных документов.
5. Обновляйте JS **и** CSS там, где приложение владеет браузерным runtime;
   проверьте доставку ресурсов, взаимодействие, доступность и вывод текста при ошибке рендера.
6. После появления согласованного артефакта установите именно его обычным
   способом, проверьте зависимости, сборку, документы и браузер. Не заменяйте
   проверку `--force`, обходом peer dependencies или `skipLibCheck`.

## Разрешение модулей в TypeScript

Выберите режим поиска модулей, учитывающий `exports`. Устаревший
`moduleResolution: "node"` / `"node10"` не поддерживается и может не найти пути (TS2307);
по старому пути тип плагина может определиться как модуль, который нельзя вызвать
(TS2349). Это настройка TypeScript, а не поддержка Node.js 10; для выполнения
по-прежнему нужен Node.js 24+.

Для кода Node.js задайте вместе `"module": "NodeNext"` и
`"moduleResolution": "NodeNext"`; пара `"Node16"` / `"Node16"` тоже поддерживается.
Сохраните формат модулей: `.cts` — CommonJS, `.mts` — ESM, а `.ts` зависит от
ближайшего `package.json#type` (`"module"` — ESM, иначе CommonJS). Не меняйте
`type` только ради поиска деклараций. Например, для ESM:

```ts
import sup from '@diplodoc/transform/plugins/sup';
import type {ParserEnv} from '@diplodoc/transform/types';
```

В `.cts`, компилируемом `tsc`, используйте `import sup = require('@diplodoc/transform/plugins/sup')`;
импорт только типа не меняется. При прямом запуске `.cts` в Node.js используйте
обычный `require()`: удаление типов в Node не поддерживает import-присваивания.
Только если приложение собирается сборщиком,
задайте `"moduleResolution": "Bundler"` с `"module": "Preserve"`; для прямого
выполнения в Node/SSR нужна отдельная конфигурация Node. `skipLibCheck` не исправляет
поиск публичных путей или ошибки вызова в коде потребителя.
См. [карту публичных импортов](../ADR/ADR-012-public-module-exports.md).

## Оценка до изменений

Запустите из корня каждого приложения или публикуемого пакета; повторите для
рабочих пространств и отдельно собираемых webview. Команды поиска показывают
кандидатов, а не полную семантическую картину:

```sh
rg -n '@diplodoc/transform|@doc-tools/transform' .
rg -n 'markdown-it|DefaultPlugins|pluginConfiguration|plugins\s*:' .
rg -n 'enableMarkdownAttrs|highlightLangs|highlighter|inlineSvg|svgInline' .
rg -n 'table_ignoreSplitters|cell-align-|notesAutotitle|directiveSyntax' .
rg -n 'parseDocument|compileDocument|\.parse\(|\.compile\(|\.meta|\.assets' .
rg -n 'transform/(lib|runtime|styles|scss)|transform/dist/' .
rg -n '\{%\s*(cut|note|list)|::: *(cut|note|tabs)|=([0-9%]*)x([0-9%]*)' .
npm ls @diplodoc/transform @doc-tools/transform markdown-it @diplodoc/utils highlight.js
```

Посмотрите также lockfile, скрипты копирования ресурсов, конфигурации сборщика,
SSR, редактор, воркеры, плагины, снимки HTML и исходные файлы документации.
`npm ls` сообщает ошибки графа; их нужно разобрать, а не считать доказательством
совместимости. При другом менеджере пакетов используйте его команды для причин
установки и разрешения пакетов. Зафиксируйте версии Node, Transform и реально
разрешаемые пути из каждого хоста.

При использовании `@doc-tools/transform` версий 2.x или 3.x отдельно оцените
фактический API, зависимости и совместимость; спланируйте необходимые этапы и
тесты. Простое переименование пакета не является миграцией на Transform 5, а
обязательность промежуточной установки 4 определяется конкретным проектом.

**Автор библиотеки:** проверьте объявленные зависимости и peer ranges, оба
поддерживаемых формата модулей, декларации, публичные точки входа и потребительскую
установку. Не расширяйте peer range до 5, пока опубликованный пакет не проверен
с настоящим Transform 5. **Автор приложения:** проверьте также транзитивные peer,
доставку runtime/CSS и все собственные сборки; версия верхнего пакета сама по себе
не доказывает, какой Transform использует каждый потребитель.

## Модули и импорты

Корневой синхронный API доступен в ESM и CommonJS:

```ts
import transform from '@diplodoc/transform';
import type {ParserEnv} from '@diplodoc/transform/types';

const output = transform('# Заголовок');
```

```js
const transform = require('@diplodoc/transform');
const output = transform('# Заголовок');
```

Используйте следующие публичные точки для нового кода:

| Назначение                                                  | Путь после `@diplodoc/transform`                                                                                                                                           |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Парсер и контекст                                           | `/parser`, `/document`, `/types`                                                                                                                                           |
| Именованная конфигурация                                    | `/configuration`                                                                                                                                                           |
| Подсветка                                                   | `/highlighter`, при переходе `/highlighter/legacy`                                                                                                                         |
| Реестр и отдельные публичные плагины                        | `/plugins`, например `/plugins/notes`, `/plugins/anchors/collect`                                                                                                          |
| Preprocessors, frontmatter, утилиты, sanitizer, логирование | `/preprocessors`, `/frontmatter`, `/utils`, `/utils/fs`, `/sanitize`, `/log`, `/deprecation`                                                                               |
| Миграция исходников                                         | `/migrations/image-dimensions`, `/migrations/table-alignment`, `/migrations/block-directives`                                                                              |
| Браузерная сборка                                           | `/browser`, `/browser/minimal`                                                                                                                                             |
| Ресурсы                                                     | `/runtime`, `/runtime/base`, `/runtime/yfm-only`, `/runtime/print`; аналогичные `/styles`, `/styles/base`, `/styles/yfm-only`, `/styles/print`; `/scss/*` и `/dist/scss/*` |

Для часто встречающихся старых импортов используйте точечное соответствие:

| Раньше                                  | Предпочтительно в новом коде                                                                 |
| --------------------------------------- | -------------------------------------------------------------------------------------------- |
| `/lib` или `/lib/index`                 | корень пакета                                                                                |
| `/lib/md`                               | `/parser`                                                                                    |
| `/lib/typings`, `/lib/plugins/typings`  | `/types`                                                                                     |
| `/lib/plugins/notes`                    | `/plugins/notes`; при самостоятельной композиции возможен `@diplodoc/notes-extension/plugin` |
| `/lib/plugins/cut`, `/lib/plugins/tabs` | стандартный preset либо публичные фабрики соответствующих расширений                         |
| `/lib/utilsFS`                          | `/utils/fs`                                                                                  |

Многие перечисленные в `exports` старые пути `lib/*` остаются совместимыми;
некоторые внутренние пути не имеют нового соответствия. Не заменяйте все `lib/`
по шаблону. Сверяйте каждый используемый путь с `exports` установленной версии и
его реальными именованными/default экспортами. Старые пути типов и явные callback
Cut/Tabs устарели и запланированы к удалению в 6; стандартные функции Cut/Tabs
при этом сохраняются. Новые `/document` и `/configuration` не имеют старого
эквивалентного alias.

`/browser` и `/browser/minimal` доступны только через ESM import; из CommonJS
используйте `await import('@diplodoc/transform/browser')`. Browser API не читает
файлы, не выполняет Liquid и YFMLint, не копирует изображения и не раскрывает
include: подготовьте содержимое на стороне хоста. Он не загружает ресурсы из
метаданных и не исполняет произвольные URL. Minimal не устанавливает встроенные
функциональные плагины; оба варианта сохраняют финальную санитизацию. Runtime и
стили подключаются отдельно.

```ts
import transform from '@diplodoc/transform/browser';
import '@diplodoc/transform/runtime';
import '@diplodoc/transform/styles';

function renderPreview(
  container: HTMLElement,
  source: string,
  reportError: (error: unknown) => void,
) {
  try {
    container.innerHTML = transform(source).result.html;
  } catch (error) {
    container.textContent = source;
    reportError(error);
  }
}
```

Пример предполагает сборщик с поддержкой JS и CSS. При любой ошибке рендера,
в том числе при нераскрытом include, показывайте исходник как текст и сохраните
принятое в приложении логирование ошибок. Если
вызывающий код ожидает строку HTML, экранируйте исходник как текст для HTML.
Проверьте компонент, который показывает результат: разделите пустой строкой
`{% include [part](part.md) %}` и `<i data-probe>text</i>`. На экране должен
появиться буквальный тег, а элемент `i[data-probe]` в DOM должен отсутствовать.
Повторите проверку с другой ошибкой рендера и убедитесь, что корректный Markdown
по-прежнему отображается как HTML.

Transform использует markdown-it 15. Если приложение передаёт свои плагины или
создаёт отдельный MarkdownIt, проверьте фактические версии и типы, порядок
регистрации, метаданные и выход. Адаптер, совместимый с отдельной версией 13,
не гарантирует совместимость всех плагинов и безопасность старой установки.

Transform поставляет собственную оптимизированную сборку исходников закреплённого
markdown-it. Её конструкторы парсера и Token отличаются от конструкторов отдельно
импортированной установки `markdown-it`. В собственных плагинах используйте
переданные им объекты парсера и состояния; проверьте сравнения конструкторов и
`instanceof` с независимо импортированным движком. Правила парсера и семантика
нативных полей классов сохранены.

### Старый импорт Liquid evaluator

Default-импорт исторического `/lib/liquid/evaluation` после CommonJS interop может
быть функцией, а в native ESM — namespace с этой функцией в `default`.
Нормализуйте форму модуля, сохранив прежний boolean evaluator:

```ts
import evaluation from '@diplodoc/transform/lib/liquid/evaluation.js';

function resolveEvaluator<Evaluator extends (...args: never[]) => unknown>(
  value: Evaluator | {default: Evaluator},
) {
  return typeof value === 'function' ? value : value.default;
}

const evaluateCondition = resolveEvaluator(evaluation);
evaluateCondition('audience == "public"', {audience: 'public'}); // true
```

Сохраните суффикс `.js`, чтобы native ESM нашёл старый путь в Transform 4.
Именованный `evalExp` возвращает исходное значение и не заменяет boolean API
напрямую. Если пакет поддерживает Transform 4 и 5, проверьте оба формата модулей.

### Свой плагин emoji

Если при регистрации `markdown-it-emoji` возникает ошибка
`md.utils.assign is not a function`, проверьте, какую копию импортирует пресет.
Версии 2.0.2 и 3.0.0 падают на markdown-it 15 ещё до разбора текста. Добавьте
`markdown-it-emoji@3.1.0` в прямые зависимости пакета, который регистрирует
плагин. Выберите именованный экспорт по прежнему пресету: `full` заменяет
импорт по умолчанию из 2.x, а `bare` подходит для своего словаря. Например:

```js
import {bare} from 'markdown-it-emoji';

md.use(bare, {defs: {wave: '👋'}});
```

Сохраните словарь, настройки и место плагина в порядке регистрации. Если другой
потребитель ещё использует markdown-it 13, сохраните его отдельный граф
зависимостей и проверьте один и тот же пример с emoji в обоих окружениях.
Запустите также проверку типов в пакете, который регистрирует плагин: версии
деклараций markdown-it у потребителей могут различаться.

## Изменения HTML после обновления парсера

При переходе с markdown-it 13 на 15 сохраняются авторские Unicode-пробелы,
включая U+00A0 (NBSP), по краям абзаца, которые версия 13 удаляла. При включённых
переносах строк сохранённый пробел перед переводом строки может также добавить
`<br />`. Это может изменить интервалы; проверьте снимки HTML и отображение.
Непреднамеренные пробелы исправляйте в Markdown, без произвольного удаления
пробелов в готовом HTML.

Обновление `markdown-it-deflist` с 2.1 до 4 может добавить обёртки `<p>` внутри
`<dd>`, например если определение содержит текст и следующий за ним список или
если термин и определение разделены пустой строкой. Короткое определение после
многоабзацного, напротив, может потерять обёртку `<p>`. Проверьте собственные
CSS-селекторы вроде `dd > p`, отступы абзацев и снимки HTML.

В списке определений выровняйте термин и маркер `:` или `~` по окружающему тексту.
В Transform 5 перед маркером допустимо до трёх дополнительных пробелов.
После пустой строки отступ в четыре пробела или больше начинает блок кода. Чтобы
в обеих версиях сохранить определение и разметку внутри него, поставьте маркер
сразу под термином. У примеров кода оставьте исходный отступ.

```markdown
**Открыть шторы**
: Задайте _расписание_.

**Приоткрыть шторы**
: Выберите процент открытия.
```

Если после термина идёт строка только с `:` или `~`, теперь получается пустое
определение. Даже строка с одним неразрывным пробелом может стать пустым термином.
Чтобы показать сам знак в тексте, напишите `\:` или `\~`.
[Изменения парсера списков определений в версии 4.0](https://github.com/markdown-it/markdown-it-deflist/blob/4.0.0/CHANGELOG.md)

## Диагностика документа и сборки

`Output.logs` теперь содержит только диагностику текущего документа и возвращает
отдельный снимок массивов. Следующие вызовы, повторное использование parser и
очистка collector не меняют предыдущие результаты. Include и дочерние фрагменты
пишут в collector своего документа. `parser.logs` показывает последний документ,
а `document.logs` — диагностику конкретного handle, включая его позднюю компиляцию.

Для истории всей сборки передайте явный collector:

```ts
import transform from '@diplodoc/transform';
import {createDiagnosticCollector} from '@diplodoc/transform/log';

const diagnostics = createDiagnosticCollector();
const page = transform(source, {path, diagnostics, log: applicationLogger});
const documentLogs = page.logs;
const buildLogs = diagnostics.get();
// Process the build snapshot before releasing its retained diagnostics.
diagnostics.clear();
```

Общий collector дополнительно накапливает сообщения; `page.logs` остаётся
снимком одного документа. `get()` возвращает копии, `add()` сохраняет порядок и
переданные дубликаты. Прежний экспорт `log` сохраняет изменяемые `get/add/clear`,
но получает только явные записи, forwarding либо `diagnostics: log`.
`log.get()` больше не собирает обычные вызовы автоматически. Setup плагинов
выполняется один раз и относится к первому документу parser. Для самостоятельных
Liquid/lint helpers без logs в результате передавайте `diagnostics` и/или
внешний `log`. Полный контракт:
[время жизни диагностики](../specs/transform-5/diagnostic-lifetime.md).

По умолчанию Transform выводит предупреждения об устаревших возможностях.
Чтобы их отключить в Node или браузере, передайте `deprecationWarnings: false`
в Transform либо `core: {deprecationWarnings: false}` в `defineTransformOptions`.
Если предупреждения включены, логгер может обрабатывать их отдельным методом
`deprecation(message)`. Существующие логгеры с тремя методами получат сообщение
через `warn`. Предупреждения также доступны в `Output.logs.warn`.

В ветке CLI с поддержкой Transform 5 сборка с `--strict` выводит такие
предупреждения и завершается успешно, если других проблем не возникло. Чтобы отключить их, передайте
`--no-deprecation-warnings` или задайте `deprecationWarnings: false` в YAML-конфигурации
CLI. Остальные предупреждения по-прежнему учитываются в строгом режиме.

## Настройки и набор плагинов

Плоские настройки и прежний массив callback `plugins` сохраняются. Собственный
массив **заменяет** стандартный список: сохраните все нужные callback и их порядок.
Для нового кода можно явно описать состав:

```ts
import transform from '@diplodoc/transform';
import {defineTransformOptions} from '@diplodoc/transform/configuration';

const options = defineTransformOptions({
  core: {enableMarkdownAttrs: true},
  plugins: {
    disable: ['video'],
    options: {notes: {notesAutotitle: false}},
  },
});
const output = transform(source, options);
```

Для расширения прежнего `plugins: [...DefaultPlugins, custom]` используйте
[пример именованной композиции](cut-tabs-types.md). Явный массив callback
по-прежнему предупреждает об устаревших Cut/Tabs. При переходе сохраните его
режимы `directiveSyntax: 'disabled'`; именованный preset по умолчанию включает
новый синтаксис.

Стандартный preset устанавливает `meta`, `deflist`, `cut`, `notes`, `anchors`,
`tabs`, `code`, `sup`, `video`, `monospace`, `table`, `file`, `imsize`, `term`,
`block-anchor`, `inline-code`, `visibility`, `underline`, `subscript`,
`footnotes`, `task-list` в этом порядке. Последние четыре включены по умолчанию;
checkbox задач недоступны для редактирования. Настройки и порядок собственных
плагинов проверяйте на своём корпусе.

| Конструкция                          | Результат по умолчанию                |
| ------------------------------------ | ------------------------------------- |
| `++text++`                           | Подчёркивание: `<u>text</u>`          |
| `H~2~O`                              | Нижний индекс: `H<sub>2</sub>O`       |
| `[^id]` и определение `[^id]: текст` | Сноска и её содержимое                |
| `- [x] задача`                       | Отмеченный checkbox только для чтения |

Если ваш прежний хост показывал эти конструкции обычным текстом и нужно
сохранить это поведение, отключите соответствующие плагины:

```ts
const options = defineTransformOptions({
  plugins: {disable: ['underline', 'subscript', 'footnotes', 'task-list']},
});
```

Для синтаксиса `++` выберите один парсер. Если нужен `<ins>` от
`markdown-it-ins`, отключите Transform `underline`; не регистрируйте оба
обработчика одной грамматики.

Если вы явно подключаете старый callback `checkbox`, отключите `task-list`
в именованной конфигурации или уберите его callback из собственного массива
плагинов. В стандартном preset старый `checkbox` не включён. При подключении обоих
callback элементы списка первым обрабатывает `task-list`; отдельные абзацы
со старым checkbox продолжают обрабатываться отдельно.

Старые метки ссылок, начинающиеся с `^`, теперь могут стать сносками:
`[^^name]` с определением `[^^name]: ...` распознаётся как сноска с меткой
`^name`. Если это обычная ссылка, переименуйте метку и в ссылке, и в определении
так, чтобы она не начиналась с `^`. Чтобы сохранить прежнее поведение всего
корпуса, можно отключить `footnotes`.

`preset: 'none'` исключает встроенные функциональные callback, но не превращает
парсер в сырой markdown-it: core-правила, preprocessors и финальная санитизация
остаются. `enable`, `disable`, `options` и пользовательские `plugins` задаются
в именованной конфигурации; настройка невыбранного плагина вызывает ошибку.
Нельзя одновременно передать старый массив `plugins` и `pluginConfiguration`,
даже если массив пуст. Не задавайте одновременно плоскую настройку и её
одноимённую настройку конкретного плагина.

Notes **остаются включены по умолчанию**, как и прежние локализованные и явные
заголовки. `notesAutotitle: false` сохраняет прежний смысл. Самостоятельный
список callback может использовать `createNotesPlugin` из
`@diplodoc/notes-extension/plugin`, сохранив formatter и опции хоста. При
замене явных Cut/Tabs callback используйте прямые зависимости и публичные
фабрики расширений; сохраните опции, `output`, `generateID`, порядок и `collect`.
Идентичность callback изменится: проверьте фильтры по ссылке. Это не означает,
что надо менять стандартный preset или импортировать второй экземпляр Notes CSS.

## Атрибуты и подсветка

Общие Markdown-атрибуты теперь выключены по умолчанию. Если документы зависят
от них, задайте `enableMarkdownAttrs: true` в плоских настройках либо
`core.enableMarkdownAttrs` через builder. Идентификаторы заголовков и размеры
непосредственно после изображения работают независимо от общего переключателя.
Проверьте пользовательские классы, идентификаторы и sanitizer.

Подсветка больше не загружается автоматически: без `highlighter` код безопасно
экранируется и выводится без подсветки. Установите совместимый Highlight.js
(peer `^10.0.3 || ^11`) и передайте адаптер явно:

```ts
import transform from '@diplodoc/transform';
import hljs from 'highlight.js';
import {createHighlightJsHighlighter} from '@diplodoc/transform/highlighter';

const highlighter = createHighlightJsHighlighter(hljs);
const output = transform(source, {highlighter});
```

Для старого `highlightLangs` передайте фабрики как
`createHighlightJsHighlighter(hljs, {languages: highlightLangs})`. Список
`allowedLanguages` ограничивает имена с учётом регистра; неизвестный язык остаётся
экранированным текстом. Загрузка языка инициализируется до синхронного вызова;
автоопределения нет. Для native ESM с выборочной загрузкой Highlight.js 10
использует пути `highlight.js/lib/core.js` и `.../languages/javascript.js`, а 11 —
`highlight.js/lib/core` и `.../languages/javascript`. Корневой импорт поддержан
для обоих. Не отключайте sanitizer ради разметки highlighter.

Разные установленные версии Highlight.js могут создавать другие классы и
вложенные элементы `<span>`, даже если текст кода не изменился. Зафиксируйте
нужную версию и проверьте стили подсветки и снимки HTML.

## Таблицы, изображения и SVG

В YFM-таблицах с положительным `header-rows` строки шапки теперь попадают в
`<thead>`. Если `rowspan` объединяет ячейку шапки с ячейкой в теле таблицы,
сохраняется единый `<tbody>`. Для выбора строк шапки в обоих случаях подходит
`tr[data-header]`. Проверьте свои CSS-селекторы и плагины, которые ищут все строки в `tbody`.

В таблицах разделитель `|` внутри распознанного inline-кода теперь по умолчанию
не делит ячейку. Для прежнего поведения пропущенной настройки задайте
`table_ignoreSplittersInInlineCode: false`; при отключённой защите block-кода
проверьте оба соответствующих флага. Если пропала строка таблицы, проверьте,
не образовали ли обратные кавычки пару в разных ячейках или строках.
В обычном тексте используйте апостроф или экранируйте буквальную обратную
кавычку. Закрывайте inline-код в той же ячейке.
[Примеры исправлений](transform-5-tables.md#if-the-next-row-disappears)

Старый суффикс выравнивания по-прежнему работает и предупреждает при фактическом
использовании. Предпочтительная форма:

```md
#|
|| Text {.cell-align-center} | Other ||
|#
```

```md
#|
||::{align="center"} Text | Other ||
|#
```

Поддержаны `top-left`, `top-center`, `top-right`, `center`, `bottom-left`,
`bottom-right`. Сохраняется CSS-класс `cell-align-*` и добавляется `data-align`.

`TABLE_CELL_ALIGN_CLASS` указывает на начало ячейки в Markdown, который получил
парсер. После обработки Liquid и раскрытия include номер строки может отличаться
от исходного. В таком случае ищите `.cell-align-*` в исходном файле и его include.

Старые размеры изображения продолжают работать с предупреждением при применении:

```md
![Alt](image.png =300x200)
```

```md
![Alt](image.png){width=300 height=200}
```

Атрибуты размера должны непосредственно следовать за изображением; возможны
`width=50%` и отдельный `height`. Они работают и при выключенных общих атрибутах.

Замените `inlineSvg` на `svgInline.enabled` и сохраните sanitizer и ограничения
entity. Если заданы оба, `svgInline.enabled` имеет приоритет, даже если это
`false`. Старый alias работает в 5 с предупреждением при использовании и
запланирован к удалению в 6.

Неполный объект `svgInline` теперь всегда наследует лимит размера файла 2 MiB.
В Transform 4 объект `{enabled: true}` мог терять этот лимит — это ошибка
нормализации. Если приложению нужно встраивать SVG большего размера, задайте
явный лимит, например 4 MiB:

```ts
transform(source, {svgInline: {enabled: true, maxFileSize: 4 * 1024 * 1024}});
```

Без явного изменения лимита файл больше 2 MiB останется ссылкой на изображение.
Атрибут изображения `{inline=true}` по-прежнему принудительно включает встраивание;
защита от XML entities и санитизация продолжают работать. Подробности — в
[ADR настройки SVG](../ADR/ADR-011-svg-inline-option.md).
Как и раньше, проверка считает длину текста SVG в единицах UTF-16; значения
в MiB соответствуют ASCII-содержимому, а не новому подсчёту байтов файла.

Для исходников доступны синхронные чистые функции:

```ts
import {migrateTableAlignment} from '@diplodoc/transform/migrations/table-alignment';
import {migrateImageDimensions} from '@diplodoc/transform/migrations/image-dimensions';

const table = migrateTableAlignment(source, {path: 'guide.md'});
const images = migrateImageDimensions(table.output, {path: 'guide.md'});
// Review both diagnostics before saving images.output.
```

Они не читают и не записывают файлы, не раскрывают include и не выполняют Liquid.
`path` — метка диагностики. `edits` содержат позиции в исходной строке в UTF-16,
с исключающей правой границей; каждый результат относится к собственному входу.
Табличный helper меняет только однозначные простые ячейки; сложные атрибуты,
объединения и вложенные таблицы требуют ручного разбора. Image helper оставляет
неоднозначные диапазоны, вложенные изображения, необычные размеры и уже
имеющиеся соседние группы атрибутов на проверку. Результаты проверьте на реальном
корпусе и с пользовательскими плагинами. Предупреждения не означают, что эти
формы удалены в 5; удаление возможно не раньше 6 при отдельных условиях.

## Необязательный переход на директивы

Cut, Notes и Tabs поддерживают старые конструкции и новые блоки с двоеточиями.
Менять документы для перехода на 5 необязательно; версия удаления старого
синтаксиса не объявлена. Пример новой формы:

```md
:::cut [Подробнее]

Текст.

:::
```

Также доступны `:::note [Заголовок] {type=info}` и `:::tabs {variant=radio}`.
У Note тип обязателен: `info`, `tip`, `warning`, `alert`; `[]` задаёт явно
пустой заголовок. В Tabs содержимое остаётся списком; варианты — `regular`,
`radio`, `dropdown`, `accordion`, выделение — `{selected}`. Каждый блок
закрывается строкой из не менее трёх двоеточий. Сначала проверьте поддержку
потребителей, особенно редактора, перевода и линтера.

Настройка `directiveSyntax` принадлежит каждому плагину: `disabled` принимает
только старую форму, `enabled` — обе, `only` — только новую. В стандартном
preset по умолчанию `enabled`; у самостоятельных фабрик расширений и явных
старых callback — `disabled`. При собственном составе настройте каждую фабрику.
Переключение не переписывает документы, а отключение плагина отключает обе формы.

```ts
import {migrateBlockDirectives} from '@diplodoc/transform/migrations/block-directives';

const result = migrateBlockDirectives(source, {path: 'guide.md'});
// Review result.diagnostics before saving result.output.
```

Функция меняет только доказанно эквивалентные пары Cut, Note и Tabs, сохраняет
нетронутые байты и не пишет файлы. Код, HTML, подтверждённо закрытый frontmatter, экранированные примеры
и обработанные include защищены. Неподдержанные атрибуты, несопоставленные или
перекрещенные блоки и неоднозначная структура остаются без автоматической замены
с диагностикой; безопасные соседние блоки могут мигрировать. Запускайте на
авторских файлах до раскрытия include, затем проверяйте результат через реальный
рендеринг, перевод и линтер. Функция не доказывает совместимость сторонних
плагинов и не меняет режим парсера.

Для Liquid действует исключение из правила безопасных соседей. Вне подтверждённо
закрытого frontmatter любое необработанное начало подстановки `{{` (в том числе незакрытое)
или неизвестный шаблонный тег `{%` оставляет **весь документ без изменений**,
без правок и с `unresolved-liquid-template` у первого такого маркера. Это касается
также кода, HTML и параметров директив: без значений и контекста шаблона нельзя
доказать независимость соседних блоков. Известные нешаблонные YFM-маркеры
проверяются своими грамматиками. Открывающий разделитель frontmatter без
закрывающего считается обычным Markdown и не защищает остальной документ.

Бюджет проверки кандидатов — **32 фактических вызова парсера на полном входе**,
включая анализ областей и профили общих атрибутов; это не 32 группы-кандидата.
Непроверенные группы остаются без замены с `equivalence-budget-exceeded` у
открывающего маркера; независимо доказанные группы могут мигрировать. Начальные
разборы и обязательная финальная проверка всего документа без кеша в обоих
профилях атрибутов не входят в этот бюджет. Частичное доказательство не разрешает
правку. При сбое финальной проверки возвращаются исходный текст, пустой список
правок и `parser-or-equivalence-failed` с offset ноль. Это причины диагностики
`BLOCK_DIRECTIVE_NOT_MIGRATED` с исходными координатами UTF-16, строкой/столбцом
и необязательным path. Наличие поддержанного синтаксиса не гарантирует миграцию
каждого вхождения. Подробности — в [публичном руководстве](../block-directives.md).

## Контекст документа и вложенное содержимое

Если один парсер используется для нескольких документов, каждый раз получайте
отдельный handle и компилируйте именно его:

```ts
import parser from '@diplodoc/transform/parser';

const md = parser(options);
const first = md.parseDocument('# Первый');
const second = md.parseDocument('# Второй');
const firstHtml = md.compileDocument(first);
const secondHtml = md.compileDocument(second);
console.log(first.env.meta, second.env.meta);
```

Настройки и плагины фиксируются при создании парсера; для других root/path/options
создайте новый. Пользовательский `generateID` сохраняет свою идентичность и
состояние. Инициализация данных конкретного документа задаётся вторым аргументом
`parseDocument(source, env => { ... })`. В правилах плагинов используйте
`state.env.meta` и `state.env.assets`, а не общее состояние парсера.

Старые `parse(source)` и `compile(originalTokens)` сохраняются; исходный массив
токенов связан со своим контекстом. Для скопированного массива задайте handle:
`md.compile(tokens.slice(), document)`. Handle другого парсера недопустим.
Ошибка renderer делает данный handle непригодным для последующей компиляции;
следующий parse получает чистый контекст. Старый `env` — перенаправляемое
представление активного или последнего успешного корня, а не объект для хранения
конкретного документа. Нет гарантии безопасных одновременных верхнеуровневых
вызовов или исправления проблем времени жизни кеша.

Для дочернего предварительно обработанного Markdown используйте
`parseDocumentFragment(md, source, state.env, options)` из `/document` и явно
задавайте в `options` назначение `include`, `fragment` или `reference` согласно
типам установленной версии. Успешные include/fragment вносят ресурсы в родителя;
reference и неудачный дочерний разбор этого не делают. Frontmatter ребёнка не
заменяет родительский. Произвольные изменяемые значения могут разделяться по
ссылке, поэтому внешние побочные эффекты не откатываются. Например, внутри
существующего правила плагина, где `md` — настроенный native MarkdownIt, а
`state` — текущее состояние правила:

```ts
import {parseDocumentFragment} from '@diplodoc/transform/document';
import type {StateCore} from '@diplodoc/transform/types';

function appendChild(state: StateCore, childSource: string): void {
  const tokens = parseDocumentFragment(state.md, childSource, state.env, {
    purpose: 'fragment',
    path: 'child.md',
  });
  state.tokens.push(...tokens);
}
```

Функция возвращает массив токенов; используйте его согласно контракту вашего
правила. Не запускайте тот же дочерний разбор рекурсивно. При кешировании
фрагментов используйте публичные `parseDocumentFragmentResult` и
`replayDocumentFragment` только с совместимым парсером; ключи, срок жизни кеша и
сопоставление исходных файлов принадлежат хосту. Не переносите непрозрачные
capsule между разными Node/browser сборками. Цикл include приводит к ошибке;
хост решает, как завершить сборку.

Для собственного MarkdownIt можно использовать `createDocumentEnv` и `envMeta`
из `/document`: передавайте новый env в каждый `md.render(source, env)` и
переносите и запись, и чтение metadata в `env.meta`. Неправильный YAML в этом
адаптере остаётся обычным Markdown; это отличается от внешнего
`markdown-it-meta`, который может бросать исключение.

## Зависимости 4 и 5 в одном приложении

Если редактор или UI имеет peer contract на Transform 4, оставьте **реальный**
Transform 4 для этого хоста. Собственный код приложения может установить 5 под
отдельным именем зависимости и импортировать её через это имя. Сверьте дерево
зависимостей и разрешение из каждого пакета: alias сам по себе не меняет peer
хоста, его parser или заранее собранные браузерные ресурсы. Для библиотеки
зафиксируйте, какая версия принадлежит вызывающему приложению, и не подменяйте
peer фиктивной декларацией или несовместимым override.

Если у Transform 4 и 5 общий пресет, перенесите фактические значения настроек
(например, разрешённые HTML-теги и атрибуты) через API каждой версии. Избегайте
приведения типов старого парсера и его callback к новым типам. Собственные
плагины и токенизатор проверьте на обоих движках, а при различиях в их
контрактах напишите отдельные адаптеры.

Utils `3.0.0-beta.2` больше не объявляет широкий глобальный индекс Window по
symbol. Предыдущие кандидаты, включая `3.0.0-beta.1`, вызывали `TS2374` при
строгой проверке совместной установки Utils 2 и 3. Обновите современную копию
Utils, сохранив реальный граф Utils 2 / markdown-it 13 у старого хоста. Исправленная
проверка пакета использует строгие ESM/CommonJS-декларации и общую очередь с
настоящими markdown-it 13 и 15. Если ваш код записывает собственные symbol-поля
в Window, объявляйте их явно: прежнего широкого ambient-индекса Utils больше нет.
Проверьте весь граф своих хостов с `skipLibCheck: false`; обход peer dependencies
или поддельные ambient declarations не заменяют эту проверку.
Аналогично проверенные локально изменения HTML host entry, Page и Gravity
требуют доступных согласованных артефактов и проверки реального графа — не
подставляйте предполагаемые стабильные номера версий.

## CSS, runtime и встроенные движки

Сборка сервера, установленный Transform и браузерный JS/CSS — разные артефакты.
Определите единственного владельца каждого runtime и stylesheet на каждой
странице и в каждом webview. Проверьте, что сборщик действительно включает или
копирует совместимые файлы, а не прежнюю готовую сборку клиента. При смешанной
разметке 4/5 проверьте оба формата и отсутствие повторных обработчиков. Данные
`meta.script`, `meta.style`, `meta.csp` — объявления ресурсов, а не разрешение
выполнять произвольные URL из документа.

Transform уже включает стили Notes; не добавляйте дубликат standalone CSS.
Для компиляции публичных Sass-исходников подключите `NodePackageImporter` Sass,
который разрешает `pkg:` импорты. Потребителям готового CSS это не нужно:

```js
import * as sass from 'sass';

const result = sass.compile('app.scss', {
  importers: [new sass.NodePackageImporter()],
});
```

Встроенные Liquid и YFMLint пока сохранены; предупреждения относятся к
фактическому использованию. Корневой Liquid работает, если не установлен
`disableLiquid` или `isLiquided`, но один `isLiquided` не отключает Liquid в
дочерних helper. Standalone YFMLint асинхронен: вызывайте его с `await` вне
синхронного конвейера Transform.

## Проверка и завершение

До изменений сохраните набор представительных исходников и их HTML/metadata:
обычный Markdown, атрибуты, подсветку и неизвестный язык, сложные таблицы,
размеры изображений, SVG, Cut/Notes/Tabs, include, footnotes, task lists,
перевод и документы с собственными плагинами. Добавьте в выборку случаи,
найденные поиском, и приложения с особыми настройками. Снимки полезны, но
отличия нужно оценить по смыслу, безопасности и ресурсам, а не принять все.

После доступности артефактов:

1. Установите согласованные версии без подавления ошибок peer; проверьте lockfile,
   `npm ls`, пути разрешения из каждого хоста и то, что версии пакетов доступны.
2. Выполните typecheck без искусственных деклараций, тесты, сборку и проверку
   опубликованного или предоставленного архива как установленного пакета.
   Проверьте ESM/CJS и поддерживаемые browser entry в нужных приложению режимах.
3. Сравните HTML, metadata, предупреждения и ресурсы до и после, включая ошибки,
   вложенные документы и независимость контекстов при повторном использовании
   парсера. Проверьте обработку отказов автоматических миграторов.
4. В настоящем браузере проверьте SSR/CSR при необходимости, светлую и тёмную
   темы, открытие Cut, переключение Tabs, Notes, подсветку и ресурсы. Отдельно
   оцените клавиатуру, ARIA, контраст и уникальность идентификаторов.
5. Зафиксируйте точные версии и результаты отдельно для исходного кода,
   установки, CI, публикации, внедрения и работающего окружения. Ошибка или
   неизвестный статус любого этапа остаётся отдельным пунктом плана.

Локальные проверки кандидата не дают общего заключения по доступности: ранее
наблюдались повторные ID у кешированных Tabs и некорректное `aria-selected` у
Dropdown Tabs; некоторые проверки контрастности также имели ограничения. Были
и существовавшие ранее ошибки деклараций Translation/CLI. Успех частной проверки
не означает, что эти ограничения устранены.
